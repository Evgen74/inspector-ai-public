# «Инспектор ИИ»

ИИ-сервис сверки проектной (ПД), рабочей (РД) и исполнительной (ИД) документации по матрице из 132 параметров.
Хакатон, задача №10 (Мосстройнадзор). Все части системы (сервер, ML-конвейер, веб-клиент, контракты) живут в одном
репозитории и работают **локально** на macOS и Linux: без внешних сервисов, без облачных LLM/OCR и без сетевых
вызовов из продуктового кода. Два способа запуска: нативно (`make dev`) или целиком в Docker
(`docker compose up -d --build`, см. [«Запуск в Docker»](#запуск-в-docker) и `docs/runbook/DOCKER.md`).

> **Публичная копия.** Из неё исключены материалы организаторов хакатона: текст ТЗ и матрицы, предметная разметка и
> её изображения (`docs/spec/`), эталоны распознавания по страницам документов организаторов
> (`docs/analysis/gt_staging/`, `ocr_gt_v2.json`), профили корпусов (в том числе скрытого тестового объекта) и
> прототипы этапа анализа (`tools/prototypes/`). Ссылки на них в `docs/analysis` ведут на отсутствующие файлы. Тесты,
> которым нужны данные организаторов, без них пропускаются. Матрица 132 параметров в виде контракта
> (`packages/contracts/seed/params.json`) включена — без неё продукт не работает.

## 1. Назначение

Сервис принимает комплект документов объекта капитального строительства, распознаёт его, извлекает значения по 132
параметрам матрицы контроля, сопоставляет актуальные редакции ПД, РД и ИД, формирует **предварительный протокол** по
Приложению 2 с карточками доказательств (страница, область на листе, значения по стадиям) и передаёт его инспектору.
Инспектор подтверждает или отклоняет каждое расхождение, финализирует протокол и отправляет подтверждённое в ИАИС «РиН»
(в этой версии — заглушка). Решения инспектора накапливаются как размеченные примеры для дообучения.

Система работает в двух режимах на одном движке:

- **`inspector-batch`** — пакетный конвейер на Python без БД и брокера: инвентаризация → распознавание → разметка →
  таблицы → сравнение → экспорт ответа (JSON) и протокола → локальная оценка (раздел 9);
- **веб-продукт** — API на NestJS + PostgreSQL + Redis + веб-клиент на React: загрузка комплекта, проверки,
  протоколы, верификация, справочники и мониторинг (разделы 10–11). Веб импортирует те же каталоги запусков.

## 3. Архитектура

```
             ┌────────────── браузер ──────────────┐
             │  apps/web  (React 19, Vite, :5173)  │
             └───────────────┬─────────────────────┘
                             │ /api/v1 (JSON, cookie-сессия, CSRF)
             ┌───────────────▼─────────────────────┐        ┌───────────────────────┐
             │  apps/api  (NestJS 11 + Fastify, :3000)      │  РиН-заглушка (mock)  │
             │  auth · RBAC · audit · upload · import ─────►│  /mock-rin/inspection │
             │  verification · protocols · monitoring       └───────────────────────┘
             └──┬──────────┬──────────┬──────────┬─────────┘
                │          │          │          │ страницы, плитки
        PostgreSQL 17   Redis 8   RabbitMQ   ml-api (FastAPI, :8090)
        (:5432, БД      (сессии,  (:5672,    рендер страниц PDF для просмотра
        inspector)      кэш)      очередь    доказательств
                                  inspector.jobs, необязателен)
                                     │
             ┌───────────────────────▼─────────────────────┐
             │ inspector-batch (Python 3.12, services/ml)  │
             │ inventory → recognize → layout → tables →   │
             │ compare → export → score                     │
             │ каталог запуска runs/<run_id>/…              │
             └─────────────────────────────────────────────┘
```

Поток данных: **загрузка** (`POST /documents/upload`, архив или файлы + реестр) → задание в очереди `inspector.jobs`
(RabbitMQ; если недоступен — выполняется внутри процесса API, режим `in-process`) → **распознавание** (текстовый слой,
OCR на ONNX, кэш токенов по sha256 страницы) → **разметка и таблицы** (штампы, QR, помещения, марки, экспликации, ТЭП,
спецификации, АОСР) → **сравнение** по матрице 132 параметров → **протокол** (Приложение 2: JSON, DOCX, PDF) и ответ
(`submission`) → **импорт** каталога запуска в PostgreSQL → **верификация** инспектором → **финализация** →
**РиН** (заглушка).

- Контракты (перечисления, схемы, коды ошибок, права, раскладка артефактов запуска, OpenAPI) лежат только в
  `packages/contracts`; Python и TypeScript читают одни и те же YAML/JSON Schema.
- Все артефакты запуска описаны в `packages/contracts/run_layout.yaml`; потребители читают `runs/<run_id>/artifacts.json`.
- Скрытая тестовая выборка защищена на уровне кода: `inspector-batch` отказывает `score` на ней и запускает
  распознавание/сравнение/экспорт только с флагом `--hidden-run`; `make guard` проверяет, что код и конфигурация не
  упоминают её идентификатор.

## 5. Требования к окружению

| Параметр | Значение |
|---|---|
| ОС | macOS arm64 — эталонный стенд, на нём сняты все замеры; Linux (Ubuntu 22.04/24.04, x86_64/arm64) — раздел 7, сборка и тесты проверяются в CI (GitHub Actions, Ubuntu); Windows не проверялся |
| Эталонный стенд (на нём сняты все замеры) | Apple M2 Max, 12 ядер, 32 ГБ ОЗУ. Минимальные требования не измерялись |
| Диск | модели 573 МБ (13 файлов, `make verify-models`); полный комплект одного объекта — порядка 2,8 ГБ (142 PDF); кэш токенов и каталоги `runs/` растут с числом обработанных страниц; на стенде на момент планирования было свободно 68 ГиБ |
| Node.js | 22 и выше; pnpm — через corepack (версия закреплена в `package.json`, поле `packageManager`) |
| Python | 3.12 (`>=3.12,<3.13`); менеджер — `uv` |
| PostgreSQL | 17 на `localhost:5432`, база `inspector` |
| Redis | 8 на `localhost:6379` (сессии) |
| RabbitMQ | необязателен: `amqp://127.0.0.1:5672` (`INSPECTOR_RABBITMQ_URL`); без него задания идут в процессе API |
| Прочее | git, `bsdtar` (libarchive) для архивов; `unrar` не использовать |
| Сеть | не нужна: никаких внешних сервисов и онлайн-моделей; менеджеры пакетов нужны только при установке зависимостей |

Распознавание использует ONNX Runtime. Исполнитель **определяется автоматически: CoreML (macOS) → CUDA (Linux/Windows +
NVIDIA) → CPU**. CUDA выбирается, только если сессия на видеокарте действительно создаётся (пробный запуск детектора),
иначе — CPU; решение пишется в лог и в консоль, проверить на машине — `make gpu-check`. Принудительно — ключ
`--providers auto|coreml|cuda|cpu` команд `recognize` и `bench` (конвейер `run` и загрузка через интерфейс
используют `auto`). На Linux x86_64 ставится `onnxruntime-gpu`
(CUDA 12, библиотеки NVIDIA — pip-колёсами, системный CUDA Toolkit не нужен; нужен драйвер NVIDIA), без видеокарты он
работает на CPU. Путь CUDA покрыт модульными тестами, **на реальной видеокарте не проверялся** (эталонный стенд — Mac).

## 6. Установка и первый запуск (macOS)

```bash
git clone <репозиторий> && cd <каталог>
cp .env.example .env                 # необязательно: пути, порты, формат логов
make setup                           # uv sync --locked, corepack enable pnpm, pnpm install --frozen-lockfile, быстрая проверка моделей
make verify-models                   # sha256 обязательных моделей из .models/ по tools/models/manifest.json
make test                            # базовый тест: должен быть зелёным
```

1. **Модели.** Каталог `.models/` не в git. Три модели OCR, без которых не работает распознавание, скачивает
   `make fetch-models` (однократно, с проверкой sha256 по `tools/models/manifest.json`; проверка — `make verify-models-ocr`).
   Полный набор (включая встраиватель для поиска гипотез) перечислен в манифесте, проверка — `make verify-models`;
   без встраивателя `make setup` запускается с `SKIP_MODEL_CHECK=1`.
2. **PostgreSQL и Redis** (Homebrew-сервисы или любые локальные экземпляры на стандартных портах), затем:
   ```bash
   make db-create        # создаёт БД inspector (идемпотентно)
   make db-migrate       # миграции apps/api/drizzle (0000…0008)
   make db-seed          # демо-учётка
   ```
3. **Запуск всего стека:** `make dev` — API `:3000`, веб `:5173` (прокси `/api` на API), ml-api `:8090` (рендер страниц).
   По отдельности: `make api-dev`, `make web-dev`, `make ml-api-dev`. Ctrl-C останавливает всё.
4. **Вход:** http://127.0.0.1:5173, логин `inspector`, пароль `Demo-Inspector-2026`
   (переменная `INSPECTOR_DEMO_PASSWORD`). В продукте **одна роль — «Инспектор»** (`INSPECTOR`), суперроль со всеми
   правами (решение владельца продукта от 29.09); миграция `0008_single_inspector_role.sql` переводит пользователей в неё.
5. **Проверка живости:** `GET http://127.0.0.1:3000/api/v1/health`, метрики Prometheus — `http://127.0.0.1:3000/metrics`.
6. **RabbitMQ** (необязательно): если сервис запущен на `:5672`, загрузка идёт через очередь `inspector.jobs`.

Локально `INSPECTOR_AUTH_MODE=optional` пропускает запросы на чтение без сессии; изменяющие запросы всегда требуют
сессию и CSRF-токен. В режимах `demo`/`prod` обязателен `required`.

Основные переменные окружения (полный перечень — `.env.example`, `apps/api/README.md`): `INSPECTOR_DATABASE_URL`,
`INSPECTOR_REDIS_URL`, `INSPECTOR_RABBITMQ_URL`, `INSPECTOR_API_HOST`/`INSPECTOR_API_PORT`, `INSPECTOR_ML_API_URL`,
`INSPECTOR_APP_ENV`, `INSPECTOR_AUTH_MODE`, `INSPECTOR_DATA_ROOT`, `INSPECTOR_RUNS_ROOT`, `INSPECTOR_UPLOAD_WORKERS`
(число процессов обработки при загрузке через интерфейс; по умолчанию — автоматически) и `INSPECTOR_RESOURCE_CAP`.

**Нагрузка на машину.** Анализ занимает не больше `INSPECTOR_RESOURCE_CAP` (по умолчанию 0,75) ресурсов: каждый пул
процессов конвейера (распознавание, разметка, таблицы, инвентаризация) получает не больше 75 % ядер (с учётом лимитов
контейнера) и столько процессов, сколько помещается в 75 % памяти из расчёта `INSPECTOR_WORKER_MEM_MB` (1024 МБ) на
процесс (`inspector_common/resources.py`). Явное `--workers` / `INSPECTOR_UPLOAD_WORKERS` действует только в этих
пределах.

**Пауза и отмена.** На странице проверки — «Пауза», «Продолжить» и «Отменить» (`POST /processes/{id}/pause|resume|cancel`).
Пауза и отмена останавливают конвейер вместе со всеми его процессами. После «Продолжить» обработка запускается снова,
а уже распознанные страницы берутся из кэша, поэтому распознавание продолжается с места остановки. Отмена окончательна.

Загрузка через интерфейс: `/processes` → «Загрузить комплект». Лимиты — **500 МБ на документ и 5 ГБ на пакет**
(ТЗ §9.1 предписывает 50 МБ и 200 МБ; лимиты подняты решением владельца продукта, чтобы полный комплект объекта
грузился одним архивом). Защита от zip-бомб: до 16 ГиБ распакованных данных.

## 9. Пакетный режим (`inspector-batch`)

```bash
cd services/ml
uv run --locked inspector-batch --help
# полный сквозной прогон обучающего объекта (или из корня: make run-train OBJECT=… RUN_ID=… ARGS="…")
uv run --locked inspector-batch --run-id <id> run --object OBJ-TYUMENSKAYA-5-GOLD-SEED --workers 2
# оценка с явным путём к ответу (без --pred берётся «последний прогон с ответом» — может оказаться старым)
make score PRED=runs/<id>/submission            # только обучающие объекты
make score-selftest                             # гейт T-GOLD: воспроизведение контрольных случаев оценщика
```

Подкоманды: `inventory`, `recognize`, `layout`, `tables`, `compare`, `export`, `score`, `bench`, `run`.
`run` выполняет цепочку inventory → recognize → layout → tables → compare → export → score в одном каталоге запуска,
останавливается на первом упавшем шаге и отказывает на скрытом объекте. Быстрый перезапуск: `--from-step recognize`
(с кэшем около 5 с); `--from-step layout` на новом `RUN_ID` даёт деградированную разметку — стартуйте с `recognize`.

**Формат ответа.** `runs/<run_id>/submission/<OBJECT>.json` — полный ответ по 132 параметрам (строка на параметр;
статусы: нарушение, нет нарушения, документ отсутствует, сравнение невозможно), рядом строгий вариант
(`submission.strict`) и sidecar; протокол по Приложению 2 — `runs/<run_id>/protocol/` (JSON, DOCX, PDF). Схемы —
`packages/contracts/schemas`, проверка — `uv run --locked inspector-contracts validate submission.strict <файл>`.

**Скорость** (измерено на эталонном стенде):

## 10. API

Контракт: `packages/contracts/openapi/openapi.yaml` (OpenAPI 3.0.3, 61 операция; дополнения-оверлеи в

| Объекты и дашборд | `GET /dashboard`, `GET /objects`, `GET /objects/{id}`, `GET /objects/{id}/files`, `GET /objects/{id}/protocols` |
| Протокол | `GET /objects/{id}/protocols/{run_id}`, `…/export?format=json\|docx\|pdf`, `GET /processes/{id}/protocol`, `GET /processes/{id}/completeness` |
| Доказательства | `GET /files/{id}/pages/{n}`, `…/image`, `…/tiles/{level}/{x}/{y}`, `GET /files/{id}/annotations` |
| Верификация | `GET /processes/{id}/findings[/{finding_id}]`, `POST …/decisions`, `GET /processes/{id}/disputes`, `POST /processes/{id}/finalize`, `…/unfinalize`, `…/verification/claim`, `…/reopen` |

Ошибки — `application/problem+json` с русским текстом и `request_id` («Код обращения»). Изменяющие запросы требуют

```bash

     http://127.0.0.1:3000/api/v1/auth/login                       # → csrf_token
curl -b jar -H "X-CSRF-Token: <csrf_token>" -H 'content-type: application/json' \
     -d '{"run_dir":"<run_id>"}' http://127.0.0.1:3000/api/v1/admin/batch-runs/import
```

Параметры сессий (idle 30 мин, абсолютный срок 12 ч, не более 3 сессий на пользователя,
блокировка после 5 неудачных входов) описаны в `apps/api/README.md`.

## 14. Ограничения и что не сделано

- **Скрытый тестовый объект не обрабатывался** — решением руководителя (29.09): распознавание остановлено на 4476 из
  15678 страниц (кэш сохранён), ответ по нему не сдаётся. Порядок, если к нему вернутся: один замороженный прогон,
  шаги `recognize`, `layout`, `tables`, `compare`, `export` отдельными командами с `--hidden-run`; содержимое до
  отправки никто не просматривает; идентификатор берётся из `split_policy.json`, в коде не хардкодится.
- **Глубина сравнения по матрице ограничена.** Все 132 строки всегда присутствуют в ответе, но содержательные
  компараторы есть не для всех параметров: реализованы сравнение значений по правилам матрицы (дельта, порядковое,
  смена перечисления), поэлементное сравнение по помещениям (семейства вентиляции), материалы КР/КЖ (класс бетона,
  арматура, толщины, F/W), допуски ИГС, ТЭП ПД↔РД, спецификации ЭОМ/ВК. На Новослободской содержательный статус
  получили 4 строки из 132 (после добавления ПЗ, КР-стали и энергоэффективности — 5), остальные — «документ
  отсутствует» или «сравнение невозможно». Извлечение и сравнение по содержанию привязаны к **75 параметрам из 132
  (72 из 106 критических)**: ПЗ/ТЭП (PZ-001…023), СПЗУ (025…028, 030, 031, 037, 038), КР (054…062, 066),
  ИОС (вентиляция по помещениям; спецификации ЭОМ/ВК/ОВ/АПС: 068, 069, 071, 073, 074, 076, 077, 078, 079, 080),
  пожарная безопасность (PPM-102…105, 107, 109, 111…114), ОДИ (116, 117, 119, 121), АР (045, 049, 050),
  энергоэффективность (ZU-124…128, 131), POS-087. Для многих из них на имеющихся реальных объектах не нашлось пары
  стадий со значениями, поэтому ветка «нарушение» проверена тестами на синтетике. Противоречивые значения одного
  параметра внутри стадии (разные файлы) выдаются как «подозрение ИИ» (раздел 6 протокола), не как нарушение.
  Не сравниваются по содержанию: размеры и расстановка по чертежам (двери, лестницы, тамбуры, извещатели), ПОС/ПОД
  (кроме POS-087), ООС, смета.
  Компаратора границ (`OUTSIDE_BOUNDS`) нет, поэтому правка порога в «Нормативной базе» находки не меняет.
- Не построены: ИГС на данных без допусков на листах, АР (площади, ширины дверей) и ГП (ТЭП) для пар ПД↔РД на реальных
  данных (проверено на синтетике). Извлечение толщин шумное; выбор конструктивных файлов ПД/РД по имени — эвристика.
- Локации КР/FREE-STRUCTURE — названия семейств («Сваи»), а не обозначения элементов из акта.
- Правило соседства марки и номера помещения проверено только на Тюменской.
- **Реальная УКЭП и ИАИС «РиН» — заглушки.** Экспорт протокола в XML не реализован.
- Единственная роль «Инспектор»; TLS, шифрование данных в покое, резервное копирование, IDS/DDoS, антивирус,
  Grafana/ELK, e-mail/Telegram-алерты, расписание очистки журнала — не реализованы (раздел 10).
- Переобучение моделей не выполняется (модуль 4 собирает данные и отчёт). Юзабилити-тест на 5 инспекторах не проводился.
- Показатели ТЗ §11 (100 одновременных инспекторов, SLA 99,9 %, RTO/RPO) не проверялись: система рассчитана на один
  локальный стенд. Время отклика API измеряется мониторингом (p50/p95), целевое значение не подтверждалось.
- Веб-клиент автоматически проверен vitest; в живом браузере проверены карточки доказательств Б.1 и Б.2 Тюменской и
  привязка по помещениям, все пункты меню руками не пройдены.
- Пометки из релизной памятки: тест `inspector_registry::test_shared_inode_with_different_hashes_is_ambiguous` один раз
  падал под xdist; загруженные файлы не чистятся (`runs/uploads/`); показатель памяти в мониторинге на macOS
  ориентировочный.

Полный перечень известных ограничений — `docs/runbook/RELEASE.md` (раздел 5); трассировка требований ТЗ —
`docs/analysis/91_tz_traceability.md`; отчёты интеграции — `docs/runbook/M1_REPORT.md`.

## 15. Структура репозитория

```
apps/api/                  NestJS-API: auth, RBAC, audit, upload, import, verification, protocols, monitoring, rin, …
apps/web/                  React-клиент (Vite)
packages/contracts/        enums.yaml, codes.yaml, errors.yaml, rbac.yaml, run_layout.yaml, JSON Schema, OpenAPI, seed матрицы
services/ml/               uv-workspace, Python 3.12
  packages/inspector_common      настройки, пути, JSON-логи, хэши, геометрия, контракты
  packages/inspector_registry    реестр манифеста, sha256, редакции, архивы, комплектность
  packages/inspector_docproc     распознавание: текстовый слой, OCR, штампы
  packages/inspector_layout      разметка чертежей: помещения, марки, слои, облака изменений
  packages/inspector_tables      таблицы, ИД, извлечение значений
  packages/inspector_compare     сравнение, экспорт, протокол по Приложению 2
  packages/inspector_hypothesis  свободный поиск, находки FREE-*
  packages/inspector_eval        оценщик inspector-score
  apps/inspector_batch           CLI inspector-batch
  apps/ml_api                    внутренний ml-api (рендер страниц)
tools/                     реестр моделей, guard скрытой выборки, прототипы анализа
docs/                      план (PLAN.md), отчёты анализа, выписки ТЗ, runbook (RELEASE.md, M1_REPORT.md)
Makefile                   точки входа; `make help` — полный список
CLAUDE.md                  правила для агентов-разработчиков
```

Ключевые правила разработки (`CLAUDE.md`): контракты — закон; данные организаторов только для чтения и не в git;
никаких сетевых вызовов в продуктовом коде; идентификатор скрытого объекта не хардкодится.
